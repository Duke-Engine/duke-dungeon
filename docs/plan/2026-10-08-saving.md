# Saving — the campaign's first foundation

Part of the campaign (`2026-10-01-campaign.md`, "What exists and what is new" item 5, "Order" 1). The owner wants
the defaults settled without asking; every choice below is one, and he may change any of them.

## The kind of save: a checkpoint, Diablo's

The game saves at **safe points**, not frame by frame. Loading **rebuilds** the world from what was saved: the floor
is generated again from its seed (generation is deterministic — same seed, same depth, same rooms), and the hero is
put back with everything he had earned.

**The ceiling:** the floor's monsters and what lies on its ground are fresh on load — the floor is the one he entered,
as it was when he entered it. What he did on it after the save is not kept. A frame-exact save (every object, every
cooldown, every buff) is a later step if the campaign ever needs one; nothing here stands in its way.

## When

- **On entering a floor** — the first floor of a run and every floor the descent opens: the autosave is written as
  the floor is laid, after the keys of the floor above are taken from the bag. A new run after a death or a win is a
  floor entered too, so the autosave then holds the fresh start: a run that ended is over, as it always was.
- **Not on quitting, yet.** The engine's pause menu ("Resume · Settings · Abandon the run") and its Quit close the
  window with no word to the game, so there is no moment to save in; asked of the engine as **E18**. Quitting loses
  only what was done on the floor since it was entered — the checkpoint's own ceiling.
- **A party is not saved.** Its heroes are other machines' players; a party save is for when the campaign decides
  whether Last Hero keeps a party (`2026-09-30-main-menu.md`).
- A load does not write the autosave again: what it would write is what it just read.

## What a save holds

| | |
|---|---|
| `Version` | the format's version; anything else is refused with a clear word, never half-read |
| `Seed` | the seed of the floor he is on — the descent's chain resumes from it |
| `Stage` | the stage's name for a stage game; absent for the descent |
| `Depth` | the floor number |
| `Hero` | the hero's template (Rogue, Knight, Mage) |
| `Experience` | everything earned this run; the **level is worked out from it** by the file's `Levelling`, so a retuned curve moves a saved hero with it |
| `Skills`, `Ranks` | the skill keys and the rank learnt in each, by key — a reordered file still lands each rank on its skill |
| `Item` blocks | the bag: each item's slot, id, level, value and extra value. The rest (name, icon, kind, what it does) is read from the item's block in the data by its id, so renaming or retuning an item reaches saved bags; an item the data no longer has is left out |

**Not saved, on purpose:**

- **Health and mana** — he arrives full, as he does on every floor the descent opens. A save is taken as a floor is
  entered, when he is full anyway; saving half a health bar would only matter for a save mid-floor, which is not one
  of the safe points.
- **Attributes / build** — they are worked out from his level and his bag, never stored on their own.
- **Buffs** — they live a few seconds.
- **The mission's step** — a save is taken at a floor's start, and a load lays the floor fresh, so the mission starts
  at its first step either way.
- **Gold** — the game has none yet.
- **Settings** — already kept by the engine in `~/.duke-engine/settings.properties`.

## Where

`~/.duke-engine/saves/` — beside the engine's settings file, the one per-user place the game and engine keep. Made
when the first save is written. Files: `autosave.duke`, and `slot1.duke` … `slot3.duke` for the manual slots once a
player can write them (E18). A save is written to a temporary file and moved over the old one, so a crash mid-write
leaves the last good save.

## Format

The project's own `.duke` text — readable, diffable, read back with the engine's `DukeText`. The engine has no
`.duke` writer, so the game writes this one small block itself (as `MapWriter` writes `.map`). No Java serialization.

```
; Duke Dungeon — a saved run.
Save
  Version = 1
  Seed = 8124402213
  Depth = 3
  Hero = Rogue
  Experience = 420
  Skills = [Q, W, E, R]
  Ranks = [2, 2, 1, 0]
  Item
    Slot = 0
    Id = Ring
    Level = 2
    Value = 6
    Extra = 0
  End
End
```

A file that cannot be read — broken text, a missing line, another version — is **refused**: the menu leaves it out
and the log says which file and why. It never crashes the game and never loads half a hero.

## What the player sees

The front menu's "Enter the dungeon" opens, when a save can be read, a first question:

- **Davom ettirish** — the newest save, its hero, level and floor under it.
- **Yuklash** — every save that can be read (the autosave, and later the manual slots), newest first.
- **Yangi o'yin** — the path the game always had: alone or a party, the descent or a stage, the hero.

With no save it asks nothing new. Every word is in `data/world/saves.duke`.

**Saqlash** (save to a slot from the game's ESC menu) waits for E18: the pause menu is the engine's and takes no rows
from a game.

## Done when

- A save written on floor entry reads back equal; a load lays the same floor (same seed → same layout) with the hero's
  level, skills and bag restored.
- A broken or other-version save is refused with a clear message, not a crash; a missing saves folder is made.
- The whole suite passes.
